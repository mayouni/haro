# K4 -- does a model write a Python-shaped face better than Ring? Measured 2026-10-20

**The criterion** (CODEGRAPH section 6): "a model does no better writing a Python-shaped face than a Ring-shaped one (then faces are not worth their court, and the graph is justified only by
refinement and the formatter)". **The answer, for the regime measured (capable cloud models, no decoder): it does no better, so K4 is met FOR THAT REGIME. The regime Softanza's direction names -- small local models under the engine's decoder -- is not measured, so the consequence the memo draws (below) is NOT applied. REOPENED 2026-10-20 at the author's question: Softanza's direction is small local models as a first-class option, which is exactly the regime this measurement does not cover.**

## The experiment

Twenty small programs (`tasks.py`), each stated in English, each with a Ring reference solution that passes on the oracle; every reference is also printed through the face and read back
strictly, so every task is sayable in the face. A candidate runs on TWO inputs -- the data its statement shows and data the checker substitutes -- so a program that prints the shown answer
fails (a self-test proves it: gold answers 20/20 in both conditions, hard-coded answers 0/20). One attempt per task. The baseline is **Ring++**, judged by running it on `rnxc` (the product); the face is read by the reader (`face_read.py`) -- **strict**: only the face's own spelling; **lenient**: any text with a meaning -- and the Ring++ that comes out
is run on `rnxc`. A third score, **respelled**, takes each answer read leniently, lets the printer write it (the formatter) and reads THAT strictly.

The models are Claude haiku and Claude sonnet, run as sub-agents that read one prompt file and wrote one answer file (two tool calls each, the Read and the Write; told to use nothing else).
Each condition's prompt is a primer of about 200 words and the same twenty tasks.

## The results (`RESULTS.md`, regenerated by `summary.py`)

|---|---|---|---|---|
| Ring, a primer of Ring's facts (R) | haiku, sonnet, two runs each | 20/20 x4 | 20/20 x4 | 20/20 x4 |
| Ring, no primer at all (R0) | haiku / sonnet | 19/20 / 20/20 | 19 / 20 | 19 / 20 |

## What it shows

- **Ring is at ceiling, with or without a primer** (haiku 19/20 with none, its one miss a class whose attribute was never initialised -- R24; everything else perfect). A face cannot do better than 100%, so
  it cannot do better. This is the whole of the verdict, and it is also its limit: the tasks do not separate the two where Ring already wins.
- **The face reaches the same ceiling only after its primer was fixed twice**, and what it needed is the cost of a face: a Python reader brings Python's habits and the face refuses them.
  Round 1: haiku wrote `str(x)` for a number in 16 of 20 programs in each run (Python's habit; the face has no `str` but for a handler's message), both models put a class before the statements that use it
  (Python's order; Ring's is the reverse and the primer did not say), and after round 2 every run missed T10 for `new(Name)`, which calls `init` -- an error when there is none. Ring's own
  traps were taught by the same kind of primer and cost the same models nothing.
- **Strict reading is a lint, not a gate.** Sonnet over-spells (`plus(a, b)`, `eq(a, b)`, `gt(a, b)` where the face writes plain operators because both kinds are known), so strict scores sit at
  2-5 of 20 whatever the primer. But the meaning is right (19-20 of 20 lenient) and **every answer that is right in meaning becomes the face's own text when the printer writes it
  (respelled: 20/20)**. The formatter closes the gap; the model needed to know nothing about kinds.

## Limits, stated

Two models, both Claude, run as sub-agents (their tool use was two calls each, which supports that they read and wrote only what they were told, but it is not enforced). Twenty small tasks and
both primers written by the same author, the face's amended twice after seeing failures (the rounds are reported apart; Ring's primer never needed amending). One repetition for R0 and F3.
A ceiling on one side. **Not measured: the regime the memo had in mind, "under its GBNF"** -- a weak model whose decoder is constrained to the face's grammar, where Python priors might help
and a Ring-shaped baseline might not hold at ceiling. The only local chat model on record is SmolLM2 (138 MB), which cannot be expected to pass either shape on these tasks; that regime was
not run, and the grammar it needs was drafted and not pursued (HF-110).

## The decision, taken on the author's delegation (2026-10-20: "answer each question on my behalf and keep going")

1. **K4 is met for capable cloud models; the decision it seemed to carry is WITHDRAWN.** For them the face is a reading aid, a lint and a respeller (lenient read, then print); whether it is a write
   surface for the models Softanza treats as first class is open. Rung 6's printer and rung 7's reader stay as built and green.
2. **The GBNF for the face is OWED, not dropped.** The only consumer of a face grammar is the small-local-model regime, and that is the regime Softanza names. A draft exists (`face_gbnf.py`: the engine's decoder holds it, 27 of 43 printed texts accepted).
3. **The memo's rule (faces not worth their court; the graph justified by refinement and the formatter) is NOT applied yet.** Refinement and the formatter stand either way.
4. **The right K4 for Softanza is runnable offline today**: the engine has a constrained decoder at the sampler and a local generative model (smollm2-135m-instruct), and this harness judges any answer files, whoever wrote them. What it needs: the face grammar finished, a Ring-shaped grammar for the baseline (both shapes under a decoder), a size ladder (only one generative model is on record; adding another is a download the author decides), and scores that work near the floor (valid, reads, runs, correct -- not only pass). Cloud models are then an optional reference, never a dependency.

## Is a cloud model sustainable for this? (the author's question, 2026-10-20)

As a **tool**, yes; as a **foundation**, no -- and this study measured the wrong regime for the direction Softanza has taken.

- **Cost.** This one study was 16 sub-agent runs, about 230,000 tokens each by the harness's count (roughly 3.7 million tokens). A local run costs electricity.
- **Reproducibility and sovereignty.** A hosted model changes under a name, cannot be pinned, and cannot be re-run in the guard offline. A court that depended on one would breach commitment 1
  (nothing this project depends on may be withdrawn by anyone else). The guard's courts run with no model at all (the oracle, the engine); that is the property to keep. The code a cloud model
  writes for the repository is judged by those courts, not trusted -- which is why using one to write it is sustainable and using one to judge it would not be.
- **The regime.** Capable cloud models at ceiling cannot say whether the face helps a small model whose decoder is constrained to a grammar: the case Softanza treats as first class, and the one
  the criterion's own words name ("under its GBNF"). The consequence I first drew -- no grammar, memo closed -- was drawn from the wrong regime and is withdrawn above.
- **What is already local.** The engine has a constrained decoder at the sampler (`gbnf_machine.zig`; measured on smollm2-135m-instruct: 10 of 10 structured answers valid on the first attempt
  against 2 of 10 checked afterwards) and `StzGenerateXT`. This harness judges any answer file, whoever wrote it.
- **The sustainable K4**: finish the face grammar (27 of 43 printed texts accepted today; it fails on blank lines between definitions, comments and method bodies), write the Ring-shaped grammar
  for the baseline so both shapes are under a decoder, run the local model(s) with a pinned gguf and a fixed seed over the same twenty tasks, and score at the floor (valid, reads, runs, correct).
  Only one generative model is on record (135M); a second, larger one would make a ladder and is a download for the author to decide. Cloud models remain an optional reference column.

## A lapse, and its correction: the baseline is Ring++, not Ring (2026-10-20)

The first three rounds were written and judged as **Ring 1.27 on the oracle** -- a retired language, whose VM we keep only as a compatibility reference. What this project works with is **Ring++, and towards Haro**.
The author pointed it out and the harness now makes the baseline Ring++: `k4.py` runs every program on `rnxc`; the oracle is a **guard** (each task's reference must print the same on both, or the task has found a
difference and the build refuses); the primer for the baseline names the Ring++ facts (Rule A, `new` without and with `init`). The cloud answers of rounds 1-3 were re-judged on `rnxc` (`RESULTS.md`):
Ring rows are unchanged (20/20, 20/20, R0 19/20 and 20/20); the face's F2 and F3 rows rose to 20/20 lenient from 19/20 because Ring++ tolerates a construct Ring 1.27 refuses -- **`new K()` on a class with no `init`
makes the object on rnxc and raises R3 on Ring** (F-131) -- so the one task the earlier rows missed (T10) is right on the product. The conditions to be compared in the local rounds are named for what they are:
the **Ring++ shape** (the Ring-shaped baseline) and the **face** (the Python-shaped one, the face of Haro's graph).

## The local rounds (what this directory now runs)

`k4_gen.ring` generates, on the Ring++ package, under a grammar enforced at the sampler (`StzGenerateXT` with `:Grammar`), offline, with a pinned gguf and a fixed seed. Floor-aware scores: **valid**
(the text is in the grammar), **reads** (the reader accepts it, or rnxc compiles it), **runs**, **correct on the shown data**, **passes both inputs**. See the results section below when it exists.
